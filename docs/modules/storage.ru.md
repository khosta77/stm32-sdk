# Хранилище — флэш-партиции

Включается флагом `STM32_USE_STORAGE` (требует `STM32_USE_DRIVERS`),
линкуется как `stm32_storage`. Декларативная карта партиций в духе
`flash_map` из Zephyr, но проверяемая через `consteval`, а не генерируемая из
devicetree: перекрытия, невыравненные границы и выход за пределы носителя —
ошибки компиляции, а к партиции обращаются по имени.

Слой целиком не зависит от CMSIS — адаптеры общаются с концептами драйверов,
а не с регистрами, — поэтому он полностью покрыт host-тестами
(`tests/host/test_partition.cpp`).

## Карта — `storage.partition`

```cpp
import sensor.w25q32;
import storage.partition;

constexpr auto kPartitions = storage::partitionTable<sensor::W25q32Spec>({
    {.name = "boot",    .offset = 0x000000, .size = 0x010000},
    {.name = "config",  .offset = 0x010000, .size = 0x001000},
    {.name = "storage", .offset = 0x011000, .size = 0x3EF000},
});

constexpr auto kConfig = kPartitions.find("config");
```

`partitionTable()` — `consteval`, та же идиома, что `gpio()` / `spi()` /
`exti()`. На этапе компиляции отвергаются:

- пустое или дублирующееся имя;
- нулевой размер;
- смещение или конец не на границе сектора (стирание такой партиции
  откусило бы кусок соседней);
- партиция, выходящая за пределы носителя;
- любая пара перекрывающихся партиций — проверка попарная, поэтому записи не
  обязаны идти по порядку.

`find()` тоже `consteval`, поэтому опечатка в имени — ошибка сборки, а не
неудачный поиск в рантайме. `count()` и `operator[]` — `constexpr`, ими
пользуется обычный цикл по карте.

Параметр типа — геометрия носителя. `sensor::W25q32Spec` подходит как есть,
потому что предоставляет `CAPACITY` и `SECTOR_SIZE`; для внутренней флэш
используется `storage::Stm32f4Geometry<12>`, описывающая смешанную раскладку
16K/64K/128K (см. ниже).

## Геометрия — `storage.geometry`

Два концепта и две модели:

- `UniformSpec` — всё, что предоставляет `CAPACITY` + `SECTOR_SIZE`.
  Оборачивается автоматически в `UniformGeometry`.
- `IFlashGeometry` — полный контракт, которым пользуется валидатор:
  `CAPACITY`, `isSectorBoundary(off)`, `sectorSizeAt(off)`.
- `Stm32f4Geometry<SectorCount>` — внутренняя флэш F4: 4×16K, 1×64K, далее
  секторы по 128K; `CAPACITY` считается из `SectorCount` (1 МБ при 12). Она
  повторяет `driver::stm32f4::InternalFlash::sectorSize()`, который является
  рантайм-методом и потому непригоден в константном выражении;
  `consteval`-самопроверка держит оба описания в согласии.

`GeometryOf<Spec>` выбирает нужное — поэтому работают оба варианта записи
`partitionTable<...>`.

## Устройства — `storage.flash_device`

`storage::IFlashDevice` — это то, что нужно слою партиций от носителя:
адресация от нуля, запись любой длины, стирание по диапазону байт. Ни один из
существующих флэш-контрактов такого напрямую не даёт, поэтому в слое два
адаптера:

```cpp
import storage.flash_device;

// Внешняя SPI-флэш.
storage::ExternalFlashDevice device{flash};   // flash — sensor::W25q32

// Внутренняя флэш.
driver::stm32f4::InternalFlash raw{12};
storage::InternalFlashDevice<decltype(raw), storage::Stm32f4Geometry<12>>
    device{raw};                              // база по умолчанию 0x08000000
```

- `ExternalFlashDevice` добавляет **многостраничную запись**, которой нет в
  драйвере микросхемы: программирование не может пересекать границу
  256-байтной страницы, поэтому длинный буфер режется по каждой границе.
  Требования сформулированы структурно (`ExternalFlashLike`), а не через
  импорт `sensor.external_flash` — так storage не тянет за собой
  `STM32_USE_SENSORS`.
- `InternalFlashDevice` переводит смещение в абсолютный адрес, которого ждёт
  `driver::IFlash`, а диапазон байт — в индексы секторов, которые принимает
  его `eraseSector(uint8_t)`.

## Представление партиции

```cpp
storage::Partition config{device, kConfig};

(void) config.erase();                        // вся партиция целиком
(void) config.write(0, {data, len});          // смещение 0 == начало "config"
(void) config.read(0, {buffer, len});

driver::stm32f4::Crc crc{*CRC};
const auto sum = config.checksum(crc);        // driver::Result<uint32_t>
```

- Смещения **относительны партиции**, ровно как в
  `flash_area_read(fa, off, ...)` у Zephyr.
- Любое обращение за её конец возвращает `Status::InvalidArg`, а не попадает
  в соседнюю партицию.
- `checksum()` прогоняет партицию через любой движок `driver::ICrc` кусками по
  64 байта — без промежуточного буфера, ради чего в `ICrc` и разделены
  `reset`/`update`/`value`. Работает одинаково с аппаратным `Crc` и с
  `SoftCrc`; оба дают CRC-32/IEEE, поэтому значение воспроизводится на
  рабочей станции через `zlib.crc32` по дампу того же диапазона.
- `size()`, `deviceOffset()`, `name()` и `erasedValue()` описывают саму
  партицию.

## Замечания

- **Никакого devicetree.** Zephyr держит `flash_map` в DTS потому, что C99 не
  умеет считать на этапе компиляции и требует внешнего декларативного формата
  плюс генератора с bindings. C++20 `consteval` даёт ту же гарантию
  типобезопасно и без дополнительной инфраструктуры.
- Имена партиций лежат во флэш обычными литералами, а поиск целиком
  происходит при компиляции — в рантайме строки никто не перебирает.
- Слой не меняет `W25q32` и `InternalFlash`: проверка границ и разбиение по
  страницам живут в адаптерах, поведение существующих драйверов прежнее.
- Заголовок партиции (magic / версия / длина / CRC) сознательно вне объёма —
  это формат данных, а не карта.

Демо: шаблон `freertos/w25q32-flash-test` пишет через партицию, показывает,
что соседняя не пострадала после полного стирания, и сверяет аппаратный CRC с
программным.
